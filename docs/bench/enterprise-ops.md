## 方法论落地对照

| 业界做法 | 本套件实现 |
|---|---|
| 状态/答案判定, 防脆弱匹配 | 断言一律读 DOM 状态或 window 真值; 无"文本包含"式弱断言 |
| 防自我作弊 | 答题/读数类案例: **答案从工具输出文本解析**, 真值由 eval 独立读取后比对 |
| 模板化防背题 | 商品/价格/退款天数/金额每次加载随机; 下单流跑两个随机实例（变体） |

| 企业六类 | 覆盖 列表过滤/排序、仪表盘读数、知识库答题、多步下单、跨店比价（表单在 daily_ops） |

## 诚实结论：小页面密集操作上我们 token 更贵（1.5x）

**这套企业夹具上对手更省**——三个案例（过滤/排序/读数）pw 明显便宜。归因：
1. 我们 navigate 默认附首屏快照（基线播种），对方只回一句"已导航"
2. 行内 `[box=x,y,w,h]` 等属性在小页面上占比大（30 行表格 = 30 组 box）
3. 小页面没有 diff/上限的发挥空间——我们的杠杆全在大页面和重复读

**完整的 token 图景因此是**: 大页面 5-57x（大表/wiki）、重复读 90x（diff）、小页面密集操作 **0.5-0.7x（我们更贵）**。
可优化方向（未做, 记下）: navigate 附加快照可选关 / box 属性按需输出 / 小页面 diff 基线收益低时提示跳过快照。

## 与其他四份基准的关系

`token-comparison`（协议层）/ `realworld`（真实站点）/ `adversarial`（能力边界）/ `daily_ops`（日常面）/ **本件（企业知识工作 + 防自欺机制）**。综合结论：能力覆盖已对齐并在两处实测反超（拖拽/富文本）；token 优势按页面规模与访问模式分化, 不再是单边叙事。
