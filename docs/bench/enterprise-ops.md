## 三方对比的结构性观察

1. **chrome-devtools-mcp 的 uid 模型成本**：无 selector/无文本定位, 一切经 take_snapshot 取 uid,
   且 **uid 按快照代际失效**（每次快照重编号, 前代作废）——agent 每个动作前都得重拍快照,
   加上 StaticText 逐节点平铺的冗长 dump, 总成本 3 倍于我们。这正是我们 ref 代际链
   （s1e3→s2e3 顺位映射, 旧 ref 不失效）解决的问题, 在他们那是每天的成本。
2. **cdt 适配器教训**（已修, 未计其产品缺陷）: label 包裹的 input 可访问名提取、
   StaticText/容器误配需角色约束、表头类可点容器在 dump 里是 StaticText 需兜底。
3. **pw 与我们的完成率持平**（21/21）, 我们 token 低 29-40%; cdt 完成率持平但 token 2-3 倍。
4. browsermcp（依赖浏览器扩展）在本 harness 不可测, 仅记录其存在。

## nav 成本修复（本基准驱动的产品修复）

首轮暴露: 小页面密集操作上我们贵 1.5x（7,777 vs 5,097）。拆解定位: **navigate 附带的
reading 全量快照占我方总花费 75%**（834 tok/次 vs 对手 120）。修复: nav 附加快照改
**interactive 视图**（行动导向, 可操作元素+box）+ 同一提取为 reading 模式播种 diff 基线
（随后首个 reading 快照命中 diff, ref 代际链续命）。复测: 7,777 → **3,581（-54%）**,
全部案例转为比对手便宜, 完成率不变。realworld 复测同向: 23.3k → 18.2k (-22%), 总比值 25x → **31x**。

## 与其他四份基准的关系

`token-comparison`（协议层）/ `realworld`（真实站点）/ `adversarial`（能力边界）/ `daily_ops`（日常面）/ **本件（企业知识工作 + 防自欺机制）**。综合结论：能力覆盖已对齐并在两处实测反超（拖拽/富文本）；token 优势按页面规模与访问模式分化, 不再是单边叙事。
